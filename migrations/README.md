# Миграции базы данных

Миграции применяются автоматически при деплое: сервис `migrate` в `docker-compose.yml`
запускает `python -m db.migrate` до старта бота и коллекторов.

## Как добавить миграцию
1. Создать файл `migrations/NNN_описание.sql`, где NNN — следующий номер (007, 008, ...).
2. Писать обычный SQL **без** `BEGIN/COMMIT`: раннер сам выполняет файл в одной транзакции
   (если команда упала, откатывается весь файл и версия не записывается).
3. Писать так, чтобы файл безопасно выполнялся повторно (`IF NOT EXISTS`, `IF EXISTS`).
4. Обновить `schema.sql` тем же изменением (для новых пустых баз).
5. `VACUUM` и `CREATE INDEX CONCURRENTLY` в транзакции не работают: первой строкой файла
   написать `-- migrate: no-transaction` (команды пойдут по одной, без `$$`-блоков).

## Команды
```
python -m db.migrate              # применить новые
python -m db.migrate --status     # что применено, что ждёт
python -m db.migrate --dry-run    # показать, ничего не меняя
```
Локально (Windows): `$env:APP_ENV = "local"` перед запуском.

## Миграции 001-006
Выполнялись вручную до появления раннера, поэтому он их пропускает (`BASELINE_VERSION = 6`
в `db/migrate.py`). Файлы 005 и 006 лежат в папке для истории. Новая база создаётся
из `schema.sql`, в нём уже есть всё из 001-006.

## Если миграция упала при деплое
`docker compose up -d --build` завершится с ошибкой (деплой в GitHub Actions станет красным),
новые контейнеры не запустятся, старые продолжат работать. Причина — в логе:
`docker compose logs migrate`.
